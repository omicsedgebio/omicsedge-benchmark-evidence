# Project 003 — Phase 2D Identity Expansion Protocol

## Status

FROZEN BEFORE PHASE 2D IDENTITY TRANSFORMATION.

## Purpose

Phase 2D applies the already-frozen biological identity layer to the
Phase 2C run-scoped benchmark evidence.

Phase 2D creates biological VARIANT identity and EVENT_VARIANT_LINK
relationships without modifying, merging, or reinterpreting the underlying
Phase 2C EVENT or OBSERVATION records.

Phase 2D is identity resolution.

It is not reliability scoring, consensus calling, technology ranking,
variant calling, or clinical interpretation.

## Identity authority

Phase 2D inherits the Phase 1B v1 biological identity definition unchanged.

Identity schema:

`phase1b-variant-identity-v1`

Exact identity method:

`PHASE1B_EXACT_NORMALIZED_ALLELE_V1`

Identity method version:

`1.0.0`

Phase 2D application version:

`1.0.0`

The deterministic VARIANT identifier continues to be derived from:

- identity schema version;
- assembly;
- contig;
- normalized start;
- normalized end;
- normalized REF;
- normalized ALT.

Sample, technology, experiment, caller, comparator, genotype, and benchmark
outcome are not components of biological VARIANT identity.

## Phase 2D event accounting

Every Phase 2C EVENT must be accounted for exactly once by Phase 2D.

An EVENT may receive one of two Phase 2D identity outcomes:

1. `EXACT_NORMALIZED_ALLELE`
2. `UNRESOLVED`

Phase 2D does not emit
`REPRESENTATION_EQUIVALENCE_SUPPORTED`.

## Exact normalized-allele eligibility

A Phase 2C EVENT may be linked to a biological VARIANT only when all of the
following are true:

1. the EVENT belongs to the frozen Phase 2C release;
2. assembly is present;
3. contig is present;
4. every OBSERVATION associated with the EVENT has a non-null normalized
   start, normalized end, normalized REF, and normalized ALT;
5. all OBSERVATION records associated with that EVENT agree on exactly one
   normalized allele tuple;
6. the normalized allele tuple is consistent with the EVENT-level lookup
   information where that lookup information exists;
7. the resulting VARIANT identifier is generated by the unchanged frozen
   Phase 1B identity implementation.

The exact identity tuple is:

`assembly, contig, normalized_start_0based, normalized_end_0based,
normalized_ref, normalized_alt`

No other field may influence the deterministic VARIANT identifier.

## Existing Phase 1B VARIANT reuse

Phase 2D must load the frozen Phase 1B VARIANT table before materialization.

If a Phase 2C exact allele produces a VARIANT identifier that already exists
in Phase 1B:

- the existing VARIANT is reused;
- no duplicate VARIANT record is created;
- a new EVENT_VARIANT_LINK may point from the Phase 2C EVENT to that
  pre-existing VARIANT.

If the deterministic identifier does not exist in Phase 1B, Phase 2D may
materialize one new VARIANT record.

Existing Phase 1B VARIANT records must remain byte-identical and immutable.

## Cross-sample identity

The same exact normalized allele may legitimately occur in HG002, HG003,
HG004, or another sample.

Therefore identical exact normalized alleles across samples may resolve to
the same biological VARIANT identifier.

This does not imply:

- identical genotype;
- identical benchmark outcome;
- identical sequencing behavior;
- identical technology performance;
- identical biological interpretation.

Those dimensions remain attached to the run-scoped evidence.

## EVENT preservation

Phase 2D must not merge EVENT records.

One biological VARIANT may link to multiple independent EVENT records.

Every original EVENT identifier, BENCHMARK_RUN identifier, EXPERIMENT
context, sample, technology, and OBSERVATION remains independently
queryable.

A shared VARIANT identifier never means the associated benchmark
observations agree.

## Ambiguous identity

An EVENT is `UNRESOLVED` when an exact single normalized allele cannot be
established safely.

This includes, but is not limited to:

- missing normalized REF or ALT;
- multiallelic source representation without one unambiguous normalized
  allele;
- inconsistent normalized allele evidence within one EVENT;
- missing required identity fields;
- any structural ambiguity that prevents exact normalized-allele identity.

An unresolved EVENT must not receive an EVENT_VARIANT_LINK.

No placeholder or guessed VARIANT identifier may be created.

## Representation equivalence

Representation-equivalence inference remains disabled.

Phase 2D must not infer biological equivalence from:

- nearby coordinates;
- overlapping intervals;
- similar REF or ALT sequence;
- left-shiftable indels;
- right-shiftable indels;
- different decompositions;
- complex haplotypes;
- visual similarity;
- shared benchmark outcome.

Different exact normalized tuples are never merged by Phase 2D v1.

A relationship between different representations is not asserted unless a
separate representation-equivalence protocol is specified, validated, and
frozen before use.

## Phase 2D outputs

Phase 2D must produce:

- new VARIANT records required by Phase 2C evidence;
- EVENT_VARIANT_LINK records for exact Phase 2C EVENT assignments;
- per-EVENT identity accounting;
- explicit UNRESOLVED accounting;
- provenance records;
- TSV and Parquet materializations;
- deterministic summary statistics;
- reproducibility evidence;
- checksum manifest;
- compact Phase 2D release archive.

The output must distinguish pre-existing Phase 1B VARIANT reuse from newly
materialized Phase 2D VARIANT records.

## EVENT_VARIANT_LINK provenance

Every Phase 2D EVENT_VARIANT_LINK must preserve at minimum:

- event_id;
- variant_id;
- benchmark_run_id;
- identity status;
- identity method;
- identity method version;
- Phase 2D application version;
- Phase 2C archive identity;
- Phase 2 source-admission lock identity;
- Phase 2 interval-panel lock identity;
- deterministic link identifier.

No EVENT_VARIANT_LINK may depend on processing order, row number, random UUID,
wall-clock time, technology ranking, or benchmark performance.

## Product semantics

Phase 2D must make it possible for Phase 2E to query one VARIANT and retrieve
all linked evidence while preserving:

- sample;
- technology;
- experiment;
- benchmark run;
- event;
- observation;
- truth/query side;
- raw benchmark decision;
- raw match kind;
- source genotype;
- source filter;
- comparator context;
- biological identity method;
- provenance.

Contradictory observations must remain visible.

## Forbidden outputs

Phase 2D must not create:

- reliability scores;
- confidence scores;
- trust scores;
- trusted/untrusted labels;
- technology rankings;
- caller rankings;
- forced consensus;
- majority-vote truth;
- clinical interpretation;
- pathogenicity assertions.

## Locked Phase 2D validation criteria

D01. The frozen Phase 1B release archive remains byte-identical.

D02. The frozen Phase 2C release archive remains byte-identical.

D03. The Phase 1B identity implementation used by Phase 2D remains
byte-identical to the hash frozen in this protocol.

D04. No Phase 1B or Phase 2C scientific record is modified.

D05. Every Phase 2C EVENT is accounted for exactly once as
EXACT_NORMALIZED_ALLELE or UNRESOLVED.

D06. Exact identity requires one complete, internally consistent normalized
allele tuple.

D07. Every linked VARIANT identifier is generated by the frozen Phase 1B
deterministic identifier function.

D08. Existing Phase 1B VARIANT identifiers are reused without duplicate
VARIANT materialization.

D09. Ambiguous or unsupported identity remains UNRESOLVED.

D10. Representation-equivalence inference remains disabled and
REPRESENTATION_EQUIVALENCE_SUPPORTED is never emitted.

D11. No Phase 2C EVENT receives more than one biological VARIANT link.

D12. Every Phase 2D EVENT_VARIANT_LINK contains complete run, identity-method,
Phase 2C release, source-selection, and interval-selection provenance.

D13. A variant-level query preserves sample, technology, experiment,
benchmark-run, EVENT, OBSERVATION, side, and raw comparator evidence.

D14. Re-running Phase 2D on the identical frozen inputs reproduces
deterministic IDs and scientific table contents.

D15. Phase 2D creates no reliability score, confidence score, trust label,
technology ranking, or forced consensus.

D16. All Phase 2D release artifacts are checksum-manifested and independently
verifiable after archive extraction.

## Outcome gate

Phase 2D receives one verdict:

`PASS`

All applicable locked Phase 2D criteria pass.

`MODIFY`

The identity architecture remains viable but a non-fatal implementation issue
must be corrected before Phase 2E.

`STOP`

Identity cannot be expanded without unsafe merging, provenance loss,
non-determinism, or scientifically unsupported assumptions.

Validation criteria may not be weakened after Phase 2D outcomes are observed
solely to obtain PASS.
